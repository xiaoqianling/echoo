# 自动消息推送平台重构计划

## 1. 规范组件目录结构

### 1.1 现有问题

* 所有组件直接放在 `components` 目录下，缺少模块化组织

* 组件文件名与组件名不一致（部分使用小驼峰，部分使用大驼峰）

### 1.2 重构方案

* 为每个组件创建单独目录，文件夹名与组件名统一（使用大驼峰）

* 组件文件改为 `index.tsx`，便于导入

* 组件样式文件放在组件目录内，命名为 `styles.scss`

* 在组件中直接导入对应的样式文件

### 1.3 重构后结构

```
client/src/shared/components/

│   ├── index.tsx

├── BannerNotification/

```

* 将所有内联样式提取到对应的 `styles.scss` 文件

## 3. 修复 Socket 消息未弹出 ToastNotification 问题

### 3.1 现有问题

* Socket 通信正常，能接收到新消息

* `handleNewMessage` 函数只将消息添加到列表，未调用 toast 服务

### 3.2 修复方案

* 在 `messagesStore.ts` 的 `handleNewMessage` 函数中添加 toast 调用

* 确保 toast 服务被正确导入和使用

* 添加适当的消息内容，包含消息标题和关键信息

### 3.3 修复代码示例

```typescript
// 处理新消息
export const handleNewMessage = (message: Message): void => {
  // 添加消息到列表
  setMessagesState((prev) => ({
    messages: [message, ...prev.messages],
  }));
  
  // 显示 Toast 通知
  import("./toast").then(({ toast }) => {
    toast.success(`收到新消息: ${message.title}`);
  });
};
```

## 4. 优化状态管理

### 4.1 现有问题

* AuthStore 中包含 TokenManager 和 AutoRefreshManager 两个内部类，职责不够单一

* `secureRefreshManager.ts` 中存在独立的刷新管理逻辑，与 AuthStore 中的 AutoRefreshManager 功能重复

* 存在动态导入依赖的情况，增加了运行时复杂性

### 4.2 重构方案

* 将 TokenManager 和 AutoRefreshManager 提取为独立服务

* 统一使用 `secureRefreshManager.ts` 的刷新管理逻辑，移除 AuthStore 中的重复代码

* 优化状态管理的依赖关系，避免循环依赖

* 为每个功能模块创建独立的 store，保持单一职责

## 5. 优化代码结构和命名规范

### 5.1 现有问题

* 文件名命名不一致（部分使用小驼峰，部分使用大驼峰）

* 代码中存在未使用的变量和函数

* 缺少必要的注释

### 5.2 重构方案

* 统一使用大驼峰命名组件和服务类

* 统一使用小驼峰命名变量和函数

* 移除未使用的代码

* 在关键代码处添加注释，说明功能和实现逻辑

* 遵循 SOLID 原则，确保代码的可维护性和可扩展性

## 6. 优化性能和安全性

### 6.1 现有问题

* WebSocket 重连逻辑可以优化，添加指数退避机制

* 刷新 token 时没有足够的安全检查

* 缺少请求重试机制

### 6.2 重构方案

* 优化 WebSocket 重连逻辑，使用指数退避算法

* 强化 token 刷新的安全性检查，限制刷新频率

* 添加请求重试机制，提高系统可靠性

* 优化资源加载，减少不必要的网络请求

## 7. 实施步骤

1. **组件目录结构重构**：创建组件目录，移动组件文件，修改导入路径

2. **样式提取和优化**：将内联样式提取到 SCSS 文件，按层级嵌套编写

3. **修复 Socket 消息 Toast 问题**：在消息处理函数中添加 toast 调用

4. **状态管理优化**：提取独立服务，移除重复代码，优化依赖关系

5. **代码结构和命名规范优化**：统一命名，移除无用代码，添加注释

6. **性能和安全性优化**：优化 WebSocket 重连，强化 token 刷新安全性，添加请求重试

7. **测试验证**：确保所有功能正常工作，样式正确显示，Socket 消息能弹出 Toast 通知

## 8. 预期效果

* 组件目录结构清晰，便于维护和扩展

* 样式与组件分离，便于统一管理和主题定制

* Socket 收到消息后能正确弹出 ToastNotification 组件

* 状态管理职责单一，依赖关系清晰

* 代码结构合理，命名规范，易于理解和维护

* 系统性能优化，安全性增强，可靠性提高
